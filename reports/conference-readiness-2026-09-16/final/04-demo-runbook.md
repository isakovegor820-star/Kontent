# Аврора — сценарии демонстрации и репетиции

## Правила безопасного показа

- Использовать отдельный синтетический аккаунт и подготовленный проект. Не показывать настоящие клиентские тексты, email, bot tokens или admin-данные.
- До выступления проверить HTTPS health, вход, выбранный проект, browser zoom 100%, calendar date и наличие нужного draft.
- Не нажимать «Опубликовать сейчас», OAuth, отправку приглашения реальному человеку, AI-генерацию с неизвестным лимитом или destructive actions.
- Макетные показатели landing называть демонстрационным примером. Запись экрана называть записью.
- После каждого изменения показывать reload или повторное открытие — toast сам по себе не доказательство.

## Подготовленные синтетические данные

- Проект: `QA · Практика арбитража и споров`.
- Личный проект владельца: отдельно, чтобы показать изоляцию.
- Draft: памятка о проверке предмета, сроков, оплаты и ответственности; текст не обещает исход спора и требует проверки документов.
- Источник/evidence: безопасная публичная ссылка либо явно «источник не указан», если демонстрируется честное отсутствие проверки.
- Команда: минимум owner; для live multi-role сценария нужны заранее созданные отдельные аккаунты author/approver/publisher.

## Сценарий 1 — «Что это за продукт»

**Задача.** За 2–3 минуты объяснить ценность, не превратив Аврору в CRM или «ИИ-юриста».

**Шаги на экране.**

1. Открыть landing.
2. Показать заголовок, контент-план, Evidence, согласование, Telegram и отдельный статус VK.
3. Навести внимание на «Демонстрационный пример» над цифрами.
4. Открыть Terms/Privacy только при вопросе, не читать их как сертификат.

**Реплика.** «Аврора связывает тему, текст, источник, версию, решение и дату публикации. Финальную юридическую оценку принимает человек».

**Видимый результат.** Аудитория понимает границы продукта до входа.

**Вопросы.** «Это CRM?» — нет. «ИИ гарантирует корректность?» — нет. «VK уже работает?» — нужен отдельный setup и live evidence.

**Ограничение.** Цифры — UI example, не кейс клиента и не ROI.

**Восстановление.** Обновить страницу.

**Offline-резерв.** Скриншоты `retest/landing-desktop-final.png` и `retest/landing-mobile-320-final.png`, явно назвать их записью проверки.

## Сценарий 2 — «Материал от текста до календаря»

**Задача.** Показать реальный рабочий результат SMM/юриста без внешней публикации.

**Шаги на экране.**

1. В подготовленном проекте открыть `/app/composer`.
2. На пустом draft показать «Черновик не заполнен» и disabled actions.
3. Ввести короткий безопасный юридический текст либо открыть заранее сохранённый draft.
4. Показать Evidence Card: источник/дата/статус либо честное отсутствие evidence.
5. Для заранее подготовленного draft открыть календарь, затем reload.
6. Повторно открыть draft из календаря и показать сохранённый текст.

**Реплика.** «Аврора не делает пустой или непроверенный текст “готовым”. В личном проекте финальное действие — решение владельца, а не заключение системы».

**Видимый результат.** Сохранённый draft существует после reload и связан с календарём.

**Вопросы.** «Можно нажать дважды?» — client/server idempotency и versioning есть, но на сцене не имитировать provider delivery. «Что при двух вкладках?» — stale version получает conflict, сервер не молча перезаписывает.

**Ограничение.** Не нажимать live publish/queue. Calendar persistence не доказывает доставку в Telegram.

**Восстановление.** Работать с копией draft; после показа удалить только созданный QA-draft либо вернуть сохранённый текст. Не удалять prepared evidence.

**Offline-резерв.** `retest/composer-empty-actions-disabled-final.png` и запись заранее проверенного calendar/reload flow.

## Сценарий 3 — «Проекты, команда и ответственность»

**Задача.** Объяснить руководителю фирмы, как разделяются пространства и роли.

**Шаги на экране.**

1. Открыть Settings → Project.
2. Показать owner/author/approver/publisher и scope текущего проекта.
3. На единственном owner показать disabled role/delete и текст о втором владельце.
4. Переключиться между QA-проектом и личным проектом; показать разные calendar/draft data.
5. При наличии четырёх подготовленных аккаунтов — показать уже принятые memberships, но не создавать реальное приглашение на сцене.

**Реплика.** «Права относятся к проекту. Последнего владельца система не даёт удалить. История решения привязана к точной версии, но обязательный второй согласующий пока не является системной политикой».

**Видимый результат.** Project isolation и предотвращение потери последнего owner.

**Вопросы.** «Можно ли отозвать доступ?» — последующие запросы проверяют membership; транзакционные writes усилены locks. «Обязательны ли четыре глаза?» — нет, это честное ограничение.

**Ограничение.** Полный browser flow invite→accept→revoke→active session не завершён.

**Восстановление.** Вернуть исходный selected project. Не менять роли подготовленной команды.

**Offline-резерв.** `retest/settings-sole-owner-final.png` и таблица RBAC из technical review.

## Сценарий 4 — «Где заканчивается автоматизация»

**Задача.** Не дать аудитории принять Studio/Autopilot за автономного юриста.

**Шаги на экране.**

1. Открыть Studio или Autopilot overview без запуска внешней генерации.
2. Показать brief, лимит, human confirmation и связь с редактором.
3. Показать, что provider health/connection — отдельное условие.

**Реплика.** «ИИ предлагает рабочий вариант. Источник, формулировка и решение проверяются человеком; отсутствие provider не подменяется успешным результатом».

**Видимый результат.** Понятна граница UI/orchestration и внешней генерации.

**Ограничение.** В текущем QA Ollama недоступен; качество/стоимость/latency не измерены.

**Восстановление.** Никаких изменяющих действий; вернуться в editor.

**Offline-резерв.** Показать static screenshot с подписью «интерфейс, генерация сейчас не выполняется».

## Репетиция неудобных вмешательств

| Просьба проверяющего | Что сделать | Критерий успеха | Если не получается |
|---|---|---|---|
| «Объясните эту цифру» | Назвать источник, период и формулу либо сказать, что число макетное | Нет выдуманного ROI | Не показывать analytics как факт |
| «Измените текст и обновите страницу» | Править QA-draft, дождаться save, reload, сверить | Текст сохранился | Перейти к prepared copy и зафиксировать failure |
| «Что будет при пустом тексте?» | Открыть новый composer | Честный статус, disabled actions | Использовать final screenshot |
| «Покажите ошибку» | Использовать безопасную required-validation или provider-not-configured state | Ошибка видима и исправима | Не симулировать fake success |
| «Перейдите в связанный раздел» | Draft → Calendar → тот же draft | Сохраняется объект и контекст проекта | Не утверждать связь без повторного открытия |
| «Удалите владельца» | Показать disabled action и объяснение | Предотвращение до запроса | Не обходить UI и не менять DB |
| «Опубликуйте прямо сейчас» | Объяснить запрет live send в QA и показать operation boundary | Граница названа до клика | Использовать запись sandbox delivery, если она появится позже |
| «Отключите интернет» | Перейти на заранее подготовленный offline set | Материалы явно названы записью | Не выдавать видео за live run |

## Финальная контрольная карта перед выходом

- Health `200 {"ok":true,"status":"alive"}`.
- Выбран правильный QA-проект; в UI нет real client data.
- Открываются landing, calendar, prepared draft и settings project.
- Empty composer показывает disabled actions.
- Bottom navigation проверена на фактическом устройстве выступающего.
- Ведущий знает no-go claims из `06-no-go-claims-and-privacy.md`.
- Есть локальные screenshots/recording; они подписаны как запись.
