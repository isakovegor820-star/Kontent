# Исправление приглашений в проект

## Цель

Получатель может принять адресное приглашение, даже если открыл его под другим аккаунтом. Интерфейс объясняет причину отказа и проводит через смену аккаунта, сохраняя исходное приглашение. Серверная проверка почты и прав остаётся обязательной.

## План и критерии готовности

1. **Текущий аккаунт и смена пользователя.** Показать почту текущего пользователя и действие «Войти в другой аккаунт». Сначала сохранить приглашение в текущей вкладке, затем дождаться успешного ответа logout и подтверждения отсутствия сессии. Только после этого открыть login. Ошибка выхода оставляет пользователя на странице с возможностью повторить попытку.
2. **Возврат после входа.** При входе или регистрации под нужной почтой вернуть пользователя к сохранённому приглашению. При HTTP 401 обновлять авторизацию и показывать действие повторного входа. Недоступность проверки сессии обрабатывать отдельно.
3. **Жизненный цикл ссылки.** Новая корректная ссылка заменяет старую без перезагрузки. Некорректный явно переданный токен не использует прежнее приглашение. Запоздалый ответ по старому токену не меняет новую страницу и не очищает новый токен. При недоступном хранилище сохранить токен в памяти и исходном фрагменте URL; не начинать выход с потерей приглашения.
4. **Окончательные и временные ошибки.** Для истёкшей, отозванной, использованной и отсутствующей ссылки дать конкретное объяснение и убрать бессмысленное повторное принятие. При несовпадении почты предложить смену аккаунта. При потере сетевого ответа не утверждать, что сервер гарантированно не принял приглашение.
5. **Настройки → Проект.** Объяснить привязку к почте аккаунта. Рядом с готовой ссылкой показывать адресата из ответа сервера. При отзыве только что созданного приглашения убирать его из блока копирования.
6. **Проверка.** Регрессионные тесты компонента и функций хранения, существующие проверки API и сервиса, lint, TypeScript и production build. Проверить интерфейс локально с синтетическими данными. Реальные приглашения пользователей в проверках не расходовать.

## Выпуск

Изменения выполняются в отдельной ветке `codex/fix-project-invitations`. После проверок результат готов к ревью. Выпуск на рабочий сайт — через существующий процесс Deploy production после зелёного CI. Сам план и локальные исправления не означают, что рабочий сайт уже обновлён.

## Результат локального выполнения

- Пункты 1–5 реализованы в рабочей копии `Kontent-project-invitations`.
- Прошли 49 тестов в 7 файлах: обработка приглашения, подтверждённая смена аккаунта, возврат после входа, HTTP 401, отложенные ответы, недоступное хранилище, терминальные ошибки, адресат готовой ссылки и её отзыв, существующие проверки API и серверного сервиса.
- TypeScript (`tsc --noEmit --incremental false`), ESLint изменённых файлов и `git diff --check` проходят.
- Полный локальный runtime запущен через `npm run dev -- --webpack` с web, worker, отдельной БД `aurora_invite_fix_test` и отдельной Redis DB. В браузере на синтетических аккаунтах проверен полный путь: отказ по несовпадению почты, сохранение приглашения, подтверждённый logout, вход под адресатом, возврат на `/invite` и успешное принятие. В БД подтверждены роль `author`, активное членство и принятое приглашение. Тестовые процессы остановлены.
- Production build (`AURORA_SENTRY_DISABLED=1 npm run build`) прошёл со штатным лимитом heap 4096 МБ: webpack-компиляция, TypeScript, сбор данных, генерация 247 статических страниц и трассировка завершились с кодом 0.
- Перед выпуском по-прежнему нужен зелёный CI; локальные проверки не заменяют CI и не запускают развёртывание.
- Рабочий сайт, реальные приглашения, адреса аккаунтов и роли участников не изменялись. Публикация и развёртывание не выполнялись.

## Границы

Не отключать проверку почты и не предоставлять доступ любому владельцу ссылки. Не изменять адреса существующих аккаунтов и состав участников для обхода ошибки. Токен не переносить в query-параметры или журналы. Для приглашения на другую почту владелец использует отзыв и создание новой ссылки.
