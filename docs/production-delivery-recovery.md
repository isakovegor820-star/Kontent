# Неизвестная доставка и восстановление публикаций

При потере ответа провайдера публикация может уже существовать. `sending` в части,
`published_unverified` в посте и `delivery_unknown` в дополнительной операции означают
неопределённость. Ни истёкший lease, ни отсутствие message ID, ни пустой список по slug
не разрешают повторную отправку. Успешные части с квитанциями сохраняются.

## Остановка и проверка

1. Остановить web mutations и все worker unit/реплики через принятый механизм
   эксплуатации. Зафиксировать безопасные IDs поста, проекта, редакции, операции и
   parts; сохранить оригинальные квитанции и состояние очереди. Не публиковать токены,
   текст пользователей и полные URL с credentials.
2. В конфигурации изолированного восстановления установить
   `AURORA_OUTBOUND_DISABLED=1`. Основной worker откажется запускать consumers. Это
   блокировка worker, не сетевой firewall и не блокировка вызовов из web: web держать
   недоступным для mutations, не передавать ему внешние credentials, запретить outbound
   сеть инфраструктурой. Отдельные worker entrypoints тоже не запускать.
3. Включённый web readiness может читать восстановленную схему; это не разрешение
   запускать публикацию. Не использовать рабочую `.env.local` в restore runtime.
4. Сверить существующий provider receipt и действующее назначение с точной одобренной
   редакцией. Telegram public feed и VK wall window не дают доказательства отсутствия
   сообщения за пределами окна. WordPress может изменить slug или читать отстающую
   реплику. Без достоверной квитанции оставить unknown и передать ответственному.

## Одноразовый restore drill

Сначала восстановить PostgreSQL, используемые медиа и необходимые ключи в отдельную
среду с запрещённым исходящим доступом. Внешний провайдер не откатывается вместе с БД:
даже `scheduled` в backup может уже быть опубликован после создания backup.

`prepare-restored-publications.mjs` читает только явно заданный `RESTORE_DATABASE_URL`,
не загружает `.env`. По умолчанию выдаёт счётчики кандидатов, не меняет БД:

```sh
AURORA_OUTBOUND_DISABLED=1 RESTORE_DATABASE_URL='<одноразовая restore DB>' node scripts/prepare-restored-publications.mjs
```

После проверки отчёта тот же script с `--apply` переводит восстановленные активные
публикационные операции в unknown, увеличивает schedule revision, оставляет успешные
квитанции, завершает опасные дополнительные действия без resend. Apply разрешён самим
script только для localhost и имени `aurora_*_restore_test`. Повтор идемпотентен.
Для существующей/production БД этот script намеренно не предоставляет обходной флаг:
нужен отдельный проверяемый операционный пакет и явный допуск владельца.

```sh
AURORA_OUTBOUND_DISABLED=1 RESTORE_DATABASE_URL='<одноразовая restore DB>' node scripts/prepare-restored-publications.mjs --apply
```

Отдельная [регрессия на свежих синтетических фикстурах](operations/delivery-and-storage-release.md#isolated-recovery-rehearsal)
задаёт `AURORA_OUTBOUND_DISABLED`, `MIGRATION_TEST_DATABASE_URL` и
`RESTORE_DATABASE_URL` одной командой. Она намеренно очищает обе схемы фикстур и
создаёт искусственные данные. Не запускать её на копии настоящего backup или как
следующий шаг после его карантина: для неё нужны две новые одноразовые БД.

Перед будущим возобновлением ответственному нужно сверить интервал backup → остановка
по сохранившимся внешним квитанциям/журналам, новые provider effects после backup,
Telegram update offset и сообщения без восстановленного receipt, почтовые outbox и
состояние media jobs. Script карантина публикаций не доказывает полноту этих источников
и всегда возвращает `resumeAllowed: false`. Нельзя удалять receipt journal или
сбрасывать unknown/offset ради повторного запуска. Новые отправки разрешаются только
после отдельного решения о конкретных операциях; автоматического таймера разрешения нет.

## Разрешение конкретного unknown

- Есть достоверный положительный receipt: ответственный сопоставляет его с проектом,
  назначением, approved revision и уже успешными частями; подготовить CAS-изменение
  только нужной операции с audit event и перед изменением реальной БД получить допуск.
- Есть подтверждённый отказ провайдера (например, валидный Telegram `ok:false`, 429):
  обычный worker повторяет только отказанную часть не раньше `retry_after`.
- Достоверного результата нет: оставить unknown. Отсутствие поста в выдаче/поиске не
  превращать в confirmed rejection. Ручная новая публикация — отдельное осознанное
  внешнее действие с зафиксированным риском дубля и разрешением ответственного.

Изолированный drill даёт измерения и проверяет механику. Он не заменяет актуальный
production backup, согласованные RPO/RTO, полученный alert и разрешение на resume/deploy.
