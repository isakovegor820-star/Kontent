## A1 — доступ к знаниям: исправлено и проверено

Проект источника определяется через канал или сайт. Доступ зависит от действующего членства; `user_id` источника остаётся авторством. Чтение требует `project.read`, создание, удаление и обновление профиля — `content.edit`. Publisher сохраняет чтение, автор и owner могут работать с общими знаниями команды.

Мутации блокируют членство, затем канал/сайт, затем источник в одной транзакции. Отзыв и смена роли конфликтуют с блокировкой членства. Внешнее чтение канала и AI выполняются вне блокировок; перед сохранением права проверяются заново. При отзыве права прежние источники и chunks сохраняются, AI reservation освобождается. Индексация запускается после commit; существующая сверка pending-источников сохраняется.

Эффективный профиль, brief, факты и подтверждённые образцы стиля читаются для общего канала проекта. Сохраняются правила выбора полей профиля, раздельный учёт фактов и голоса, исключение RSS из стиля, квоты и ручная корректировка профиля. Новая схема БД не требуется.

## A3 — переключение проекта

Единый `ProjectDto` используется списком проектов, созданием, клиентским parser и сериализацией текущего контекста. GET/PUT `/api/projects/current` возвращают `id`, а принятие приглашения дополнительно возвращает такой же выбранный проект, сохраняя прежнее поле membership. Внутренний `projectId` сервиса не становится несовместимым HTTP DTO.

При ошибке или timeout после возможного commit provider перечитывает серверный контекст. Пока он неизвестен, рабочий экран inert; доступно отдельное действие восстановления. Sequence/epoch исключают поздние ответы старого refresh и предыдущего аккаунта. Изменение проекта пересоздаёт рабочий экран и отправляет существующее событие обновления данных. Создание проекта использует idempotency key и не навязывает выбранность проекта при replay.

На baseline три из четырёх проверок API → JSON → исходный клиентский parser воспроизводят несовместимость, создание уже работало (`../evidence/a3-baseline-reproduction`). После изменений 32 соседних unit-теста прошли (`a3-contracts`), types и lint прошли (`a3-types`, `a3-lint`).

`npm run test:projects:browser` проверяет настоящие ProjectProvider и ProjectSwitcher в Chromium, Firefox и WebKit с локальным искусственным HTTP API. Во всех трёх движках прошли переключение, потеря PUT-ответа после commit, отсутствие клика по inert-экрану при ошибке GET и восстановление. Результат и PNG: `../evidence/a3-browser`. Это компонентная браузерная проверка; полный путь приложения с PostgreSQL/Redis относится к A7.

Полный unit-прогон A3: 591 файл, 3194 теста прошли (`../evidence/a3-unit-all`).

Привязка каждого HTTP-запроса к проекту в момент действия реализована в A4 ниже. Блокировка интерфейса A3 сама по себе не заменяет серверную изоляцию двух вкладок.

## A4 — проект в момент действия

Серверный выбор аккаунта больше не определяет проект HTTP-запроса. 224 project-метода из 290 явно экспортированных методов проходят `withProjectRoute`. Обязательный `x-aurora-project-id` либо URL-селектор выбирает проект; актуальное членство и право проверяют существующие сервисы. AsyncLocalStorage переносит этот селектор через вложенные вызовы. Чужой project ID объекта не заменяет контекст запроса. Полный реестр с правами, клиентами и мутациями: [project-route-inventory.md](project-route-inventory.md). Статическая проверка не позволяет оставить новый project-маршрут без обёртки; отдельная проверка origin охватывает и обёрнутые обработчики.

Клиент захватывает аккаунт, project ID и epoch экрана. Смена или согласование проекта прерывает его запросы, блокирует старые callbacks и отбрасывает запоздалые ответы, включая отложенный JSON/body. Сервисы с несколькими HTTP-шагами используют один захваченный fetch. Store подтверждает конкретный project ID через `/api/projects/:id`, а не перечитывает изменившийся выбор другого устройства. Кэши Studio, первого запуска, generated media, подключения Telegram и анализа сайта разделены по аккаунту и проекту.

Закрыты соседние legacy-пути: идеи и конкуренты по проекту канала; приватные экспорты дополнительно проверяют проект; Radar сохраняет project ID запуска; AI проверяет канал и проект до replay/ACK; RSS использует подписку канала, не переносит строку другого проекта при одинаковом URL, а очередь ручного сбора хранит project ID. История Studio хранится отдельно для проекта и участника с versioned save и блокировкой членства при записи. Автоматизация сохраняет свои правила согласия на публикацию.

Медиа по неизменяемому URL авторизуются через проект asset ID. OAuth callback использует проект, записанный при старте, и повторяет проверку в транзакции. Telegram `startchannel` не передаёт проект: после добавления бота пользователь подтверждает именованный проект кнопкой в личном чате; нажатие повторно проверяет права обоих администраторов Telegram и owner-права проекта. Смена выбранного проекта до этого подтверждения не перенаправляет подключение. Реальные сообщения для проверки не отправлялись.

Миграция 113 сохраняет исходную account-историю Studio, копирует её только в personal-проект автора, добавляет project ID старым Radar-запускам и заменяет область уникальности RSS. Обновление полного снимка схемы A3 до A4 выполнено в новой пустой БД с уникальным именем. История и RSS-строки побайтно сохранены на уровне значений, backfill проверен, одинаковый RSS URL доступен в разных каналах, readiness подтверждает все 113 миграций. Доказательства: `../evidence/a4-migration/preservation.json`, `a4-migration-new-db-verified`. Первая попытка проверки была остановлена автоматическим review из-за возможной очистки существующей базы; выполненная версия создаёт только новую базу без очистки прежних.

## A5 — VK закрыт для неподтверждённых отправок; шифрование при reconnect исправлено

Статус: воспроизведено → исправлено → проверено для Telegram-релиза. База изменения: `29f4fd5`.

Официальная [схема `wall.post` VK API 5.199](https://github.com/VKCOM/vk-api-schema/blob/master/wall/methods.json) указывает тип токена `user`; [схема `groups.getById`](https://github.com/VKCOM/vk-api-schema/blob/master/groups/methods.json) допускает также `group` и `service`. Проверено 7 сентября 2026. Следовательно, прежняя форма с токеном сообщества и одним metadata lookup не доказывала возможность публикации. Новый поддерживаемый auth flow, проверка scopes/роли и разрешённый sandbox smoke остаются условиями **отдельного VK-релиза**. Этот пакет их не подменяет и live-ready не выставляет.

- Общий неизменяемый реестр закрывает VK livePublish, firstComment и commentToggle с причиной `vk_auth_flow_unverified`, даже при заявленных ready credentials. Read-only аналитика и сверка неизвестных прошлых отправок сохранены.
- Подключение отвечает 409 до чтения тела, обращения к VK и записи токена. В настройках убраны форма неподтверждённого токена и обещание работающего автопостинга; существующие каналы показывают причину и доступное действие — Telegram для новых публикаций.
- Новая publication operation, retry поста, перенос операции и retry дополнительных действий проверяют реестр. Отмена сохранённых VK-операций по-прежнему разрешена. Основной worker и отдельный worker дополнительных действий проверяют поддержку до отметки внешней отправки и вызова провайдера. Существующие данные не удаляются; неподдерживаемое задание получает объяснимую ошибку без автоматического повтора. Ранее подтверждённые результаты остаются подтверждёнными; неизвестный предыдущий результат дополнительного действия требует ручной сверки.
- Хранилище VK credentials использует сохранённый `channels.user_id` для AAD при переподключении другим owner. Актуальное project.manage, блокировка членства, сериализация reconnect, запись envelope и аудит находятся в одной транзакции. Сохранение токена само по себе не меняет состояние канала на active и не снимает auth error.

Токены искусственные; реальных запросов VK нет. В этом тесте явно подменён только release gate, чтобы проверить закрытый участок сохранения credentials; это **не** доказательство VK live readiness. Первая попытка обнаружила 6 устаревших ожиданий VK live support и один таймаут интерфейсного теста при одновременной полной нагрузке; expectations переведены на фактическую Telegram-площадку, добавлены отдельные проверки блокировки VK. ## A6 — полный календарь по диапазону проекта

Статус: воспроизведено → исправлено → проверено. База изменения: `6b256bc`.

GET `/api/posts` и `/api/drafts` поддерживают `view=range&from=YYYY-MM-DD&to=YYYY-MM-DD`: полуоткрытый интервал локальных дат проекта, до 62 дней. Сервер сам читает timezone проекта и преобразует границы через Temporal; переданный устаревший timezone отклоняется. Отдельные `view=undated` и `view=attention` возвращают записи без даты и записи с ошибками/неподтверждённой доставкой/запрошенными правками со всех дат. `id` позволяет открыть конкретный пост из глубокой ссылки в рамках того же авторизованного проекта.

Каждая страница содержит максимум 200 элементов и явные `hasMore`/`nextCursor`. Курсор связан с ресурсом, проектом, диапазоном и timezone; сортировка по неизменяемому ID и верхняя граница первой страницы исключают дубли при равных датах и добавление новых высоких ID в уже начатый обход. Новые записи появятся при следующем обновлении. Это живое чтение, а не долговременный MVCC-снимок: параллельные изменения содержимого становятся видны при обновлении календаря. Права проверяются на каждой странице.

Календарь загружает все страницы видимой недели/месячной сетки (включая соседние дни), бездатных записей и проблемных записей. Отдельный блок показывает требующие внимания записи вне периода. Транспорт захватывает проект на весь обход; sequence и epoch отбрасывают старый период, аккаунт и ответы в обратном порядке. Новый набор показывается после завершения всех страниц. При ошибке следующей страницы сохраняется предыдущая полная выборка **этого** периода, явно отмечается неполнота; первая неудачная загрузка показывает ошибку и неизвестное количество, а не пустой календарь. Доступен повтор. В календаре дата, подписи времени и перенос относятся к timezone проекта, даже если браузер или старая запись имеют другой timezone.

Store не загружает всю историю на экране календаря: диапазоном управляет календарь. Остальные существующие потребители постов и списка черновиков проходят все страницы и сохраняют прежнюю сортировку отображения. Удаление, согласование и публикация продолжают использовать действующие серверные сервисы.
