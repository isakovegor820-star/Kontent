## Implemented AI controls and their limits

The refundable product allowance is independent of the durable monetary attempt ledger. Every covered paid boundary reserves before the provider request. Retries and fallbacks receive their own entries, including paid failures and rejected outputs. Current membership/role and unarchived project checks apply at admission; the web and worker share one role policy. A durable user/project actor is required for queued jobs. Shared public-corpus work needs explicitly configured system user/project identifiers with active membership, and counts toward the same global cap. No ambient owner/project fallback is invented.

User, project and global daily monetary and concurrency controls serialize in PostgreSQL. Unknown provider usage, partial output, cancellation and process death retain the conservative bound. A lease expiry releases concurrency, not money. Actual reported usage is accounted even if it exceeds a prediction. Missing budgets, tariffs, attributable context or active permissions reject the paid call before contacting the provider. This deliberate configuration gate is not evidence that the feature may be silently excluded from the agreed release.

The complete variable/model inventory and read-only invoice reconciliation procedure are in [ai-spend-control.md](ai-spend-control.md). Synthetic fixture values under `src/e2e/fixtures` are not approved production amounts. Provider model parameters, reasoning token semantics, tariffs, service-side account limits and invoice allocation must be checked against the actual enabled services. No paid provider calls or contracts were used as evidence for the local implementation.

### Interactive generation cancellation and recovery

For Studio and Composer, a live request with the same key returns `request_in_progress` without starting another provider attempt. A browser Stop, departure or disconnected response does not prove that the provider did no billable work. Before releasing the separate product allowance, the server records `ai_generation_cancelled` for that exact user/request. The key then returns a terminal, non-retryable response across reload and restart. If cancellation cannot be recorded, the allowance reservation is retained. A running operation whose matching reservation is missing, expired or replaced returns terminal `ai_generation_interrupted`; reacquiring a usage row cannot reassign the old operation to a new provider attempt.

The terminal cancellation can close the same request's retryable failure when those writes race. It cannot overwrite a staged result awaiting ACK or an acknowledged result. Such results remain available through the existing authorized replay/ACK flow. The monetary ledger keeps unknown spend even when the product allowance is returned.

Studio offers **«Начать новый запуск»** only after a terminal cancellation/interruption response. That explicit action creates and persists a new request key; subsequent Library reloads retain the chosen key and source revision. Composer retains the captured key until it receives the terminal response; the next explicit generation action can create a new key. All new attempts still pass current project/role and spending checks. During support investigation, use the stored operation/request IDs, status and spend records. Do not clear a terminal marker, replace a request key automatically or refund unknown monetary usage merely to retry.

The permanent regressions are in `src/e2e/ai-project-authorization.integration.ts`, the generate/artifact/session tests and the full `scripts/test-e2e-real.mjs` journey. Their runtime results must be taken from the exact candidate's evidence; these procedures do not assert live billing reconciliation or production readiness.

Source/evidence authorization and deterministic factual checks reduce unsafe automatic publication. They cannot demonstrate live editorial accuracy, absence of hallucination, protection against every prompt injection, or correct handling of every legal claim. An owner-approved corpus, acceptance threshold, model configuration and capped live evaluation are separate release prerequisites. Outputs and source excerpts must be reviewed in the context of the feature being enabled.
